# Rust Remote Control

Workspace edition 2024: `core` (`rc-core`) содержит модель и локальное состояние, `tui` (`essence-rc-tui`) — библиотека терминального меню без зависимости от `rc-core`, `bin` (`essence-rc`) — единственный исполняемый файл (CLI, serve, меню). Версия встраивается из корневого `VERSION`; запуск не вызывает Bash.

```sh
cd remote-control
cargo build --workspace --locked
cargo test --workspace --locked
cargo run --bin essence-rc -- status --json
```

Терминальное меню: `essence-rc` без аргументов в терминале (stdin и stdout — терминал).
Меню работает в том же процессе (библиотека `essence-rc-tui`), а ядро запускает
дочерним процессом `std::env::current_exe()` + `serve --inner` (JSONL v2, без поиска в `PATH`).
В перенаправленном stdin/stdout запуск без аргументов не включает меню. Подробности — раздел шага 8.

## Команда status

`essence-rc status [--json]` читает локальный снимок без сети и без создания отсутствующего каталога данных. Начальный снимок содержит группы `ROUTER`, `PC`, `MOBILE`, без нод и клиентов. JSON-конверт: `id: null`, `ok`, `data` либо `error` с `code` и `message`. Неизвестная команда завершается с кодом 2; ошибка состояния — 1; требование авторизации — 2.

Поля сводки соответствуют ядру Bash: `version`, `update`, `script_password`, `source`, `counts`, `password_missing`, `ssh_setup_pending`, `subscription_host`. Последнее поле — имя ноды, не объект хоста. Повреждённый отдельный пароль отмечается в `password_missing`; некорректный контейнер паролей завершает команду ошибкой. Обновления не запрашиваются: `latest: null`. `source.sync` — состояние открытой GitHub-сессии (`clean|pending|offline`), для local — `null`.

Если `auth.txt` содержит поддерживаемый хеш, `status` требует пароль запуска (`script-password` через `--secrets-stdin` или скрытый ввод с консоли; иначе `auth_required`). Повреждённый хеш также блокирует доступ. Библиотечная функция сводки предназначена для уже авторизованного вызывающего кода.

## Каталог данных и схема

Приоритет имеет `ESSENCE_RC_DATA_DIR` (пустое значение запрещено). Иначе используется `dirs::data_dir()/essence-remote-control`: Linux/Termux — `$XDG_DATA_HOME` или `$HOME/.local/share`, macOS — `~/Library/Application Support`, Windows — `%APPDATA%`. Старый Bash-каталог автоматически не импортируется и не удаляется.

Реализованные файлы и ресурсы:

- `config.json`: схема 2, типизированные ноды, группы, клиенты, подключения, подписки и заголовки;
- `manifest.json`: схема 2, минимальная версия, переносимость, доступ, метаданные шаблонов;
- `secrets.json`: схема 1, карта `node_passwords`;
- `secret.key`: случайный машинный ключ длиной 32 байта;
- `auth.txt`: PHC-хеш Argon2id;
- `source.json`: необязательные строгие метаданные GitHub; отсутствие означает local;
- `templates/`, `ssh/identities/`, `ssh/known-hosts.json`;
- `.rc-lock/owner`: служебное владение блокировкой.

Модель использует обычные serde-структуры с явными доменными полями: включая aliases, credentials, client connections, subscription timestamps и заголовки уровня конфигурации/группы/клиента. Отсутствие, `null` и значения по умолчанию нормализуются; сохранение произвольных неизвестных полей и миграция старых форматов не поддерживаются. Канонические валидаторы имён, SSH-параметров и тегов применяются при загрузке и записи. Unicode-теги разрешены, управляющие и служебные символы запрещены. Пины имеют типизированные ключи `[host]:port`, **включая порт 22**, и проверенные SHA256-отпечатки; разные порты не разделяют доверие.

## Запись, секреты и авторизация

Запись публикуется через закрытый случайный временный файл в том же каталоге: запись → `sync_all` → атомарная замена. Ошибка до публикации сохраняет предыдущий файл и удаляет временный; ошибка синхронизации каталога после публикации не означает откат. Unix синхронизирует родительский каталог. Windows использует `MoveFileExW` с `WRITE_THROUGH`; эквивалентной Unix directory-fsync гарантии при потере питания нет.

На Unix новые файлы имеют 0600, каталоги — 0700. На Windows owner-only DACL задаётся **при создании**, без внешних ACL-команд; файловые системы без постоянных ACL отклоняются. Симлинки и reparse points не принимаются как чувствительные конечные назначения. На Unix доверенные существующие родительские пути канонизируются: стандартный macOS `/var` и симлинки в родительском HOME не блокируют работу. Windows-пины каталогов разделяют read/write-доступ для совместной работы процессов, запрещают delete/rename и после настройки DACL не удерживают право WRITE_DAC. Это защита локальных файлов, не изоляция от другого кода с полномочиями того же пользователя.

`secret.key` создаётся только при первой записи пароля; существующий пустой контейнер не мешает инициализации. При непустом контейнере потерянный/повреждённый ключ не заменяется автоматически. Ключ AES-256-GCM — SHA-256 машинного ключа, значение контейнера — base64 от nonce (12 байт), ciphertext и тега (16 байт). Идентификатор `node:<32hex>:ssh-password` входит в authenticated associated data: перестановка шифротекстов между нодами не проходит проверку. При каждом сохранении используется новый nonce. Прикладные открытые пароли и буферы ключей обёрнуты в `Zeroizing`; это не обещание полного стирания всей памяти процесса или внутренних состояний сторонних криптобиблиотек.

`auth.txt` содержит Argon2id v19 с профилем приложения: m=19456 KiB, t=2, p=1, соль 16 байт, результат 32 байта. Другие параметры, в том числе огромные корректно закодированные стоимости, отклоняются **до** дорогостоящей проверки. Пароль запуска и SSH-пароли не помещаются в вывод сводки.

## Блокировки и API

`State` владеет единым `LockManager`. Для вложенных операций используйте `State::secret_store()` и `State::auth_store()`: они разделяют тот же менеджер. Сессия может передать менеджер через `State::with_locks`. Конструкторы отдельных хранилищ требуют явного менеджера; создавать независимый менеджер внутри уже открытой транзакции нельзя.

Блокировка основана на атомарном mkdir, без flock. Повторный вход разрешён одному потоку через общий менеджер; другой поток или процесс не считается повторным входом. Mutation освобождается при нулевой глубине; Session сохраняется до `release_all` или уничтожения последнего владельца. `RC_LOCK_WAIT` принимает 1–6 десятичных цифр, по умолчанию 30 секунд, опрос — 200 мс. Занятая сессия отклоняется сразу.

Владелец содержит PID, время рождения процесса и случайный токен. Linux использует start ticks из `/proc`; доступный boot ID усиливает различение перезагрузок. Если boot ID закрыт (важно для Termux), одинаковые start ticks при неполной информации трактуются консервативно как живой процесс. macOS использует `proc_pidinfo`; Windows — минимальные права `OpenProcess`, нулевой wait и creation FILETIME. Отказ доступа или неопределённый результат **не** доказывают смерть владельца.

Доказанно мёртвый владелец освобождается через выборы `.reclaim`, проверку идентичности каталога и переименование в уникальный `.rc-lock.stale.*`. Отсутствующий owner допускает восстановление только после 60 секунд. Некорректный owner и брошенные выборы блокируют операцию; ошибка содержит путь и указание проверить отсутствие других операций перед ручным удалением. Действующие блокировки вручную не удаляют.

## Шаг 3: нативные SSH-эффекты

`RemoteTransport` / `RemoteSession` отделяют эффекты от команд; `SshTransport` использует russh и russh-sftp без Bash, `ssh`, `scp` или дочерних процессов. `connect` принимает пароль, файл ключа с необязательной passphrase либо системную идентичность: нативный SSH-agent (Unix-сокет / Windows OpenSSH named pipe), затем стандартные файлы `~/.ssh/id_*`. Секреты передаются в памяти; структуры аутентификации не реализуют Debug/Serialize, ошибки не включают тексты ошибок библиотек с потенциальными секретами.

Host-key callback сравнивает SHA256-отпечаток с явным пином либо известными пинами выбранного `[host]:port`; доверие автоматически не записывается. Явный неверный пин возвращает `host_key_mismatch`, смена известного ключа — `host_key_changed` с `host`, `port`, `fingerprints`; отсутствие доверия — `host_key_unknown`. Отсутствующий пароль — `missing_secret`, отсутствующий/непригодный ключ — `needs_setup`. Удалённые сбои возвращают `remote_failed` с `reason`; истечение общего срока операции — `reason: "timeout"`, не успешный exit status. `exec` одновременно передаёт stdin и читает stdout/stderr, сохраняет ненулевой exit status. Timeout закрывает только канал команды; удерживаемая через `hold` сессия не требует повторной аутентификации после уничтожения исходного транспорта.

Рекурсивный SFTP-upload передаёт бинарные файлы и назначает `.sh` режим 0755 независимо от локальной ОС и существующих прав назначения. Симлинки и конфликтующие типы назначения отклоняются. Посторонние удалённые файлы сохраняются; обычные файлы заменяются на месте, без общего отката. Корневой `VERSION` публикуется последним через временный файл и POSIX rename; без поддержки атомарной замены существующий `VERSION` сохраняется с ошибкой. `ServerBundle` разворачивает встроенные `setup-essence.sh`, `modules/`, `common/`, `VERSION` во временный закрытый каталог. `FakeTransport` предоставляет строгую очередь эффектов и журнал без содержимого credentials/stdin.

Локальная проверка на Linux:

- `~/.cargo/bin/cargo build --workspace --locked` — успешно.
- `~/.cargo/bin/cargo test --workspace --locked` — 80 core-тестов, 11 процессных тестов состояния, 1 CLI-тест и **6 реально выполненных loopback SSH/SFTP-сценариев**, без ошибок. `ssh_wire` входит в обычный набор без env-флага: пароль/ключ и отказы, системный ключ в изолированном HOME (Unix), `missing_secret`/`needs_setup`, pin/mismatch/changed/unknown, двусторонние 8 MiB stdin/stdout/stderr с exit 37, общий timeout и повторное использование соединения, отсутствие exit status, survival удерживаемой сессии после отзыва credentials, вложенные бинарные файлы, исполняемые режимы и VERSION-last при сбое публикации. Оставшиеся fake/bundle-тесты проверяют отказы, отсутствие секретов, права и очистку временного дерева, а не копирование исходников или перенаправление scripted-ответов.
- Одноразовый `~/.cargo/bin/cargo run -p rc-core --example bundle_inventory --locked` — 25 файлов, точное совпадение байтов и плоской раскладки, отсутствие standalone installer, удаление временного дерева. Пример и его каталог после проверки удалены; постоянного inventory/source-copy теста нет.

OpenSSH-сценарий `ssh_e2e` без `E2E_SSH=1` возвращается сразу: его зелёный результат обычного запуска **не является** OpenSSH-проверкой. Реальная проверка с Debian sshd выполняется CI-фикстурой `tests/ci/ssh_e2e.sh`; локально она не запускалась. Нативные агенты, зашифрованные ключи и SSH runtime Windows/macOS/Android локально не проверялись. Сборка сообщает upstream future-incompat warning для `proc-macro-error2 v2.0.1`; ошибок сборки/тестов нет.

## Шаг 4: диспетчер, конверт, serve v2 и CLI

`rc_core::dispatch::dispatch(argv, secrets, session)` — единая точка выполнения для разового CLI и serve. Конверт: `{"id","ok","data"|"error":{"code","message",…},"sync"?}`; `id` назначает транспорт, `sync` зарезервирован для успеха в GitHub-режиме (шаг 5). `RcError{code,message,extra,exit}` — единственный тип ошибки ядра: выход 2 для `usage`, `host_key_unknown`, `plan_changed` и `*_required`, 1 для прочих; коды Telegram 3/4 вводятся вместе с доменом Telegram. Поля JSON выводятся в порядке объявления (`serde_json/preserve_order`).

**Грамматика** (`rc_core::cli`): одна таблица каталога A.1 служит и разбору, и справке; каждая команда разбирается clap-командой, построенной из своей строки каталога (builder API, не derive). Переименования v2: `sub` → `subscription`; `--name` — единый селектор объекта команды (`conn`/`awg`/`telegram` — нода, `subscription show|publish|rotate|revoke` — клиент, `subscription host|migrate` — нода); связи (`--node` у `client connections|nodes`, `--group`, `--client` у `generate`/`subscription headers`) остаются. `generate` — bare-noun. Глобальные `--json --yes --plan-token --secrets-stdin --help/-h` допустимы в любом месте; `--flag=value` и `--flag value`, повтор одиночного флага, значение с переводом строки, NUL, `--`, неизвестный флаг и лишний аргумент — `usage`. Флагов с секретными значениями нет. Обязательность флагов проверяют обработчики доменов (как `cli_require*` в v1). Справка — русские тексты `_cli_help_*` v1 с заменами v2; строка `telegram install|refresh-ip|…` разбита по глаголам.

**Подтверждение** (`rc_core::confirmation`): область — `noun verb` и исходные аргументы без позиционных noun/verb, `--json`, `--yes`, `--plan-token[=T]` и транспортного `--secrets-stdin`; токен — первые 16 hex SHA-256(область`\n` + строки плана`\n` + extra). Паритет проверен литеральными токенами, полученными запуском `_rc_confirm_scope` и `rc_plan_token` из v1 (кириллица, непустой extra, раздельный `--plan-token T`, bare-noun). Без `--yes` — `confirmation_required{plan,plan_token}`, чужой токен — `plan_changed`, `--yes` без токена — согласие, `--plan-token` без `--yes` — `usage` уже при разборе. До согласия — только проверки и чтение.

**Секреты** (`rc_core::request_secrets::Secrets`): JSON-объект строк только из списка `password`, `current-password`, `vault-password`, `new-vault-password`, `script-password`; значения в `Zeroizing`, без `Debug`/`Clone`/`Serialize`, ошибки не содержат ключей и значений. Команда принимает только свои секреты; разовый CLI дополнительно принимает для защищённых команд `script-password`/`vault-password` (секреты открытия сессии, в v1 приходили через транспорт). Разовый CLI получает секреты только из `--secrets-stdin` либо скрытым вводом с консоли (crossterm raw mode, Unix и Windows, до трёх попыток на секрет, только если stdin — консоль и ядро ответило `auth_required|auth_failed|missing_secret` с подсказкой `extra.secret`). Подтверждения с консоли не запрашиваются: ввод `y` ничего не подтверждает. Переменных окружения с паролями нет.

**Сессия**: разовый CLI открывает сессию сам; отсутствующий каталог данных — открытая пустая локальная сессия (поведение шага 2). serve требует `session open` (`session_closed` иначе). «Настроено» = есть `config.json` или `source.json` (как в v1; с шагом 5 `auth.txt` больше не считается конфигурацией — её создаёт `source init-local`). Открытие источника GitHub описано в разделе шага 5.

**Журнал** (`rc_core::log`): обработчики пишут в приёмник сессии; serve превращает записи в `{"id","event":"log","level","text"}` с id активного запроса до ответа, разовый CLI печатает их в stderr с префиксами v1 (`[*] [✓] [!] [✗]`) — и при `--json`, stdout занят одним конвертом. C0/C1 вырезаются. Пишут: `session open`, `self password-set|password-remove|update|uninstall`.

**serve v2** (`essence-rc serve [--inner]`): hello `{"event":"hello","protocol":2,"version":V}`, запросы `{"id","argv","secrets"?}` строго по одному, ровно один ответ, пустые строки пропускаются. Неразборчивая строка или неверный id — `usage` с `id:null`; при корректном id ответ сохраняет его и для неверного `argv`/`secrets`/NUL (как v1). `--secrets-stdin` в argv — `usage` с id. Строка запроса читается в стираемый буфер. SIGINT перехватывается на всё время serve и разовой команды (регистрация синхронная), SIGPIPE игнорирует среда Rust; EOF закрывает сессию, exit 0; паника — один ответ `failed` для активного id без payload.

**Команды шага 4**: `help`, `status`, `session open|status`, `self version|update|uninstall|password-set|password-remove`. `self update`: метаданные `releases/latest` (rustls, `GITHUB_TOKEN` только заголовком в памяти) → план → после согласия загрузка ассета `essence-rc-<target>.tar.gz|.zip` и `SHA256SUMS`, проверка SHA-256, извлечение и атомарная замена собственного бинарника (Unix — rename в том же каталоге; Windows — переименование старого, `MoveFileExW`, откат). `self uninstall`: удаляет только текущий бинарник и с `--remove-data` каталог данных v2; корень, HOME, его предки, предки бинарника и каталоги Bash-версии отклоняются (`unsafe_path`). root требуется только если каталог бинарника недоступен на запись (v1 требовал root всегда). Ассеты релиза появятся в шаге 9; до этого `self update` честно отвечает `update_failed`.

**Не перенесено** (разбор есть, ответ `not_ready`, выход 1; должно исчезнуть к cutover): `awg *`, `telegram *`, `group *`, `template *`, `client *`, `generate`, `subscription *` (шаг 7). `!tty`: `node shell` реализован в шаге 6, `telegram menu` — в шаге 7.

Проверка на Linux (`~/.cargo/bin/cargo build --workspace --locked` и `~/.cargo/bin/cargo test --workspace --locked`): 100 unit-тестов core (грамматика, секреты, литеральные токены v1, диспетчер с журналом, архивы обновления и замена бинарника во временном каталоге), 11 процессных тестов состояния, 18 процессных тестов `cli_contract` (каталог целиком, нарушения грамматики, пароль запуска, жизненный цикл подтверждения со stdin `y`, serve v2, журнал, `self uninstall` только на одноразовой копии бинарника, proptest argv: выход ∈ {0..4}, одна JSON-строка, состояние не меняется при отказе), 4 теста `serve_protocol`, 6 loopback SSH и 3 unit-теста рендерера — без ошибок. Смоук вручную: пакет serve (hello, status, мусорная строка, неизвестное существительное, EOF → exit 0) и разовый цикл `self password-set --secrets-stdin` → `session open` → `confirmation_required` → `--yes --plan-token`; токен смоука совпал с литералом Bash v1. `self version|update` в этом окружении видели только недоступные метаданные релиза (`checked:false`; `update_failed`, `stage:metadata`): реальная загрузка и замена из релиза GitHub, Windows-замена/удаление и скрытый ввод с консоли локально не выполнялись.

## Шаг 5: источники конфигурации local и GitHub

Код: `rc_core::github::{exec, store, vault, switch, commands}`; единый путь мутаций — `Session::mutate` в `dispatch.rs`.

**Раскладка.** Локальный источник — корень каталога данных (`source init-local` создаёт `config.json` и `manifest.json`). GitHub: `source.json`, `github-store/` (bare-зеркало: `heads/main`, `heads/session/<id>`, `remotes/origin/main`, `archive/*`), `github-sessions/<id>/worktree`, `github-runtime/` (материализованное рабочее состояние: те же файлы, пароли зашифрованы машинным ключом), `credentials/gh/<login>/` (изолированные профили gh), `credentials/github-config.agekey` (только `--remember-key`), `account-switch/` (журнал смены аккаунта), `import-backups/` (прежние локальные файлы после `github-switch-local`). `auth.txt`, `secret.key`, `source.json` и блокировка всегда в корне; для открытого GitHub `Session.state` указывает на `github-runtime/` с тем же `LockManager`.

**Репозиторий.** `storage.json` `{"storage_version":1,"encryption":"age"|"none"}`. age: `recipient.txt`, `unlock.age` (файл ключа формата age-keygen, зашифрованный scrypt-паролем), `state.json.age` (снимок на x25519-recipient), всё крейтом `age` без внешних утилит. none: `config.json`, `secrets.json` (схема 2, пароли открытым текстом), `manifest.json`, `ssh/known-hosts.json`, `templates/*.yaml`, `ssh/identities/<id>{,.pub}`. Дерево и индекс git проверяются allowlist-ом (симлинки, спецфайлы, лишние пути — ошибка). Снимок формата 1: `vault_version`, `minimum_remote_control_version` (2.0.0), `portability`, `access`, `config`, `secrets`, `templates{name:{content,source,sha256}}`, `ssh{identities,known_hosts}`. Расшифрованный снимок существует только в памяти; ключ сессии — в памяти. Цепочка миграций формата существует, зарегистрированных шагов нет (формат 0 → `github_format_outdated`, `github-migrate-format` → `github_format_invalid`).

**git/gh.** Дочерние процессы через `std::process::Command` без shell: удалены `GH_TOKEN GITHUB_TOKEN GH_HOST GH_ENTERPRISE_TOKEN GITHUB_ENTERPRISE_TOKEN SSH_ASKPASS GIT_DIR GIT_WORK_TREE GIT_INDEX_FILE`; gh — `GH_CONFIG_DIR=credentials/gh/<login> NO_COLOR=1 GH_PROMPT_DISABLED=1`; git — `GIT_TERMINAL_PROMPT=0 GIT_ASKPASS=` (пустое значение git пропускает) и `-c core.askPass= -c credential.helper= -c credential.https://github.com.helper=!gh auth git-credential -c credential.https://github.com.username=<login>`; сеть — 30 с. Токен импорта (`gh auth token` → `gh auth login --with-token`) передаётся только через pipe. Диагностика редактируется (`[скрыто]`), не длиннее 500 символов.

**Синхронизация.** Открытие: блокировка `session` на всё время GitHub-сессии → восстановление журнала смены аккаунта → проверка аккаунта и приватности → `fetch --no-tags origin main:refs/remotes/origin/main` → равны: `clean`; локальная впереди: `pending`; локальная позади: fast-forward; разошлись: `source_failed` (этап «сверка локальных и удалённых изменений»), без слияния; сеть недоступна: `offline` (или `pending`, если есть неотправленный commit). Мутация: блокировка → изменение → checkpoint манифеста → сериализация → запись в worktree (сбой — откат файлов runtime и `auth.txt`) → stage allowlist → commit `Essence Remote Control <remote-control@localhost>` → `update-ref` локальной ветки до сети → `push refs/heads/session/<id>:refs/heads/main`; сбой отправки — результат команды сохраняется, `sync:"pending"`. Конверт успеха в GitHub-режиме несёт `sync`; `status.source.sync` заполнен. Закрытие сессии отправляет отложенное, удаляет worktree и снимает блокировку.

**Команды.** `source init-local|status|github-accounts|github-login|github-connect|github-fetch|github-push|github-change-account|github-rewrap-password|github-rotate-key|github-import-recovery-key|github-switch-local|github-replace-with-local|github-migrate-format|github-delete-repo`; `session open` открывает GitHub (`vault_password_required|invalid`, `github_format_*`, `locked`, `source_failed`). Решения — флаги и секреты; отсутствующее решение — `*_required` (`repo_create_required`, `repo_private_required`, `storage_mode_required{choices}`, `new_vault_password_required`, `existing_config_action_required{choices,remote_counts,local_counts}`, `cache_skip_required`, `target_replace_required{repo,tracked_files}`, `key_provisioning_required{nodes}`, `github_auth_required{login,hint}`) до изменений; неудачный connect удаляет созданное (новый каталог данных исчезает целиком). Создание репозитория, приватизация, замена, хранение без шифрования, ротация, удаление — после `Plan::confirm`. Разовый CLI спрашивает скрытым вводом и `vault-password`/`new-vault-password`. Смена аккаунта ведёт журнал `prepared → push_unknown → target_committed → local_committed`; при следующем открытии `push_unknown` проверяется по удалённой ветке (нет ветки или другая история — откат; ожидаемый commit или потомок — завершение), прежний репозиторий не меняется.

**Отличия от v1.** Онбординг нод при `github-connect`/`github-replace-with-local` (`--provision-keys yes|no`) выполняет шаг 6 (`rc_core::nodes::setup`); с `no` ноды публикуются с `needs_setup` (`missing_identity`, `missing_host_key`, `missing_secret` вычисляются при сериализации). Встроенные шаблоны встроены в бинарник (шаг 7) и разрешаются без файлов; снимок несёт файлы `templates/` состояния (пользовательские шаблоны). `known_hosts` — JSON-карта отпечатков. Снимки журнала `account-switch/old-state.sealed`/`target-state.sealed` (в них пароли нод) зашифрованы машинным ключом `secret.key` по схеме `secrets.json` (AES-256-GCM, AAD = роль файла + случайный id транзакции из `transaction.json`); ключ создаётся при первом использовании по правилам `SecretStore` (не заменяется при непустом контейнере паролей). Отсутствующий или неподходящий ключ при восстановлении — `source_failed` без изменений: журнал сохраняется для ручного восстановления. Экспорта ключа восстановления в каталоге команд нет (как в v1).

**Проверка (Linux).** `~/.cargo/bin/cargo build --workspace --locked` и `~/.cargo/bin/cargo test --workspace --locked` — без ошибок: 113 unit-тестов core (в т.ч. векторы C2SP age testkit `x25519`/`scrypt`, редактирование диагностики, allowlist дерева, классификация форматов, проверка снимка, plain round-trip с материализацией, журнал смены аккаунта, изоляция окружения git/gh), 18 `cli_contract`, 11 сценариев `github_source`, 4 `serve_protocol`, 11 `state_process`, 6 `ssh_wire`, 3 unit-теста рендерера. `github_source` (`harness = false`) — настоящий git, «GitHub» — локальные bare-репозитории через `url.insteadOf` в тестовом глобальном git-конфиге, `gh` — сам тестовый бинарник первым в PATH (падает, если в его окружение попал токен): подключение к пустому репозиторию с `*_required` без каталога данных, offline → `pending` → `github-push` → `clean`, fast-forward, расхождение историй, откат материализации, age (неверный/верный пароль, `--remember-key`, rewrap, ротация, импорт ключа), форматы newer/outdated и `replace-with-local`, второе устройство с `--existing`, `switch-local`, `delete-repo`, смена аккаунта с отказом push и восстановлением в обе стороны, цели смены аккаунта (`--replace-target`, `--existing remote`), вход через браузер, serve с удерживаемой сессией. **github.com в тестах не вызывается.** Бинарник `age` в окружении отсутствует: тест совместимости с age CLI пропускается (печатает причину), совместимость формата проверена только векторами спецификации. Windows, macOS, Android и настоящий GitHub/gh не проверялись. `cli_contract` запускает бинарник с пустым PATH, чтобы команды GitHub не достали настоящие git/gh.

## Шаг 6: ноды и подключения

Код: `rc_core::nodes::{mod, basic, add, delete, scripts, harden, setup, shell, conn}`; PTY-канал — `RemoteTransport::interactive` (`transport.rs`, `ssh.rs`, `fake_transport.rs`), консоль — `bin/src/terminal.rs::TerminalConsole`.

**Команды.** `node list|show|aliases|rename|tag|password|add|trust-host-key|delete|check|upload-scripts|harden|setup-ssh|shell`, `conn list|set|sync`. Все изменения состояния — через `Session::mutate` (local: checkpoint манифеста; GitHub: снимок → commit → push, `sync` в конверте). SSH — только через `RemoteTransport` (russh); производственный транспорт создаётся в диспетчере, тесты подставляют `FakeTransport`.

**Ключи серверов.** Пины только в `ssh/known-hosts.json` по `[host]:port`. Проверку выполняет сам handshake: `host_key_unknown`/`host_key_mismatch`/`host_key_changed` с `{host,port,fingerprints}` (отпечаток сервера) и без записи. `node add` закрепляет только согласованный отпечаток (`--host-key`, `--accept-new-host-key` — повторное подключение с закреплённым отпечатком, `--replace-host-key` — план и согласие). `node trust-host-key` — подключение с ожидаемым отпечатком, план, согласие, затем запись; снимает `missing_host_key`.

**Удаление.** План и согласие до любых удалённых действий; аутентифицированное соединение удерживается (`hold()`) как канал восстановления вместо ControlMaster; отзыв управляемого ключа, затем `bash /root/essence-setup/setup-essence.sh uninstall --force`; при сбое ключ возвращается через удерживаемую сессию и проверяется новым входом, нода сохраняется. Одна мутация удаляет ноду, подключения, ссылки клиентов, `subscription_host`, пароль, пины (если адрес не используется другой нодой), проблемы переносимости и файлы ключа.

**Усиление и SSH-настройка.** `node harden`: порт в плане детерминирован (без `--port` — первый свободный из последовательности по id ноды, 49152–65535), `port_in_use{port}`; фазы apply → verify (новое подключение к новому порту с управляемым ключом) → при сбое rollback через удерживаемую исходную сессию (резервная копия `sshd_config`, `sshd -t` перед перезапуском); `hardening_failed{stage,rolled_back,console_required}`, `console_required:true` — только если откат не подтверждён. Состояние записывается одной мутацией после проверки. `node setup-ssh` (GitHub): `nothing_pending`, `key_provisioning_required{nodes}`, план с отпечатками серверов, ed25519-ключ в `ssh/identities/<id>{,.pub}`, установка в `authorized_keys` (идемпотентно), проверка входа новым ключом, откат с отзывом ключей, `--on-failure defer`, `onboarding_failed{node,step,rolled_back}`. Тот же API используют `node add` (GitHub, вход по ключу) и `github-connect`/`github-replace-with-local`.

**Скрипты и меню.** `node upload-scripts`: проба каталога `/root/essence-setup`, сравнение с `VERSION`, `--force` — план и согласие, загрузка встроенного комплекта одной SFTP-операцией (`ServerBundle`, VERSION последним), проверка версии после загрузки. `node shell`: без консоли или в serve — `tty_required` без SSH; иначе подключение, обновление скриптов, PTY (`TERM`, размер, window-change, реальный exit status) с меню `setup-essence.sh`; raw mode консоли восстанавливается на всех путях, включая панику.

**Подключения.** Обнаружение — один `cat /etc/mihomo/client-config.txt` на ноду (без отдельной пробы `echo ok`), разбор только YAML-ключей `name:`. `conn set` заменяет группы на месте одной записью; `conn sync` сначала опрашивает ноды, затем по одной мутации на изменённую ноду, чистит и `clients[].connections` (запись клиента остаётся, даже пустая), `partial{nodes,ok,failed,total,stopped_at}`.

**Исправленные ошибки v1.** Переименование и удаление ноды обновляют `subscription_host`; случайный порт harden до плана (токен никогда не совпадал); `ufw/firewall-cmd` через `&&`; `PasswordAuthentication`/`Port` дописывались в конец `sshd_config` (могли попасть в `Match`); откат через `sed` вместо резервной копии; GNU-only проба порта; неэкранированный ключ в grep/awk; склейка последней строки `authorized_keys`; отзыв без проверки; ключ оставался на сервере после сбоя harden; пины удалялись при общей точке `[host]:port`; `--accept-new-host-key` + `--replace-host-key` принимались; `conn sync` держал блокировку на время SSH, переписывал неизменённый конфиг и терял причину сбоя; разбор обнаружения ловил прозу и строки `type: hysteria2`; две SSH-сессии на ноду при обнаружении; raw mode скрытого ввода не восстанавливался при панике.

**Проверка (Linux).** `~/.cargo/bin/cargo build --workspace --locked`, `~/.cargo/bin/cargo test --workspace --locked` — без ошибок: core 154 (из них тесты нод на `FakeTransport`: каскад переименования, trust-host-key mismatch/plan без записи, add unknown/mismatch/changed без записи, откат транзакции add, delete с восстановлением ключа через удерживаемую сессию, upload-scripts, setup-ssh успех/откат/defer, harden стабильный токен/`port_in_use`/откат через удерживаемую сессию/`console_required`, shell с PTY и `tty_required`, conn set/sync/partial), `ssh_wire` 7 (включая PTY round trip с вводом, resize и exit status на loopback-сервере russh), `cli_contract` 18, `github_source` 11, `serve_protocol` 4, `state_process` 11, bin 4. Не проверялись: настоящие серверы (команды sshd/ufw/firewalld/`setup-essence.sh uninstall`), вход сгенерированным ключом на настоящем sshd, Windows-консоль (не компилировалась), путь `node add` с выдачей ключа в режиме GitHub (нет теста).

## Шаг 7: клиенты, генерация, подписки, AmneziaWG, Telegram

Код: `rc_core::protocols` (чистые билдеры `uri`, `hy2`, `vless_tcp|grpc|xhttp`, `dnat`, `listener_users`), `rc_core::clients` (`groups`, `templates`, `client`, `generate`), `rc_core::subscription` (`commands`, `remote`), `rc_core::awg`, `rc_core::telegram` (`status`). Диспетчер больше не содержит заглушки `not_ready`: каждая команда каталога выполняется, неизвестная — `usage`.

**Билдеры и golden.** `remote-control/core/tests/protocols_golden.rs` воспроизводит все 292 случая `tests/golden/protocols/*.json` (stdout побайтно и rc; для разборщиков URI — и строки stderr; DNAT — выполнением Rust-текста команд под теми же заглушками). Исключение — два случая IPv6-DNAT, где golden фиксирует ошибку Bash (`iptables … --to-destination 2001:db8::5:443`): Rust использует `ip6tables` и `[addr]:port`, тест проверяет, что ошибка в golden всё ещё есть, и сравнивает с исправленным текстом.

**Шаблоны.** Встроенные `remote-control/core/templates/*.yaml` компилируются в бинарник; пользовательский файл с тем же именем имеет приоритет; импорт/экспорт не следуют по ссылкам, не-UTF-8 отклоняется.

**Генерация.** `generate --all|--group|--client`: по одному соединению на ноду (пиры AWG → конфигурация ноды → синхронизация пользователей listener), конфиги клиентов в `<данные>/generated/<group>/<client>/config.yaml` (0600, без ссылок); недоступная нода — `partial{ok,skipped,failed,nodes_ok,nodes_failed,dir}`, прежний конфиг клиента сохраняется. `awg status|sync|remove` (remove — план и согласие).

**Подписки.** `subscription host|list|show|headers|publish|publish-all|rotate|revoke|migrate`: токен 64 hex сохраняется только после загрузки, проверка HTTP после публикации (`partial` со ссылкой), ротация/отзыв/миграция/очистка — план и согласие, `publish-all` сохраняет новые токены одной мутацией. Нет хоста — `not_configured`, нет сгенерированного конфига — `needs_setup`, на ноде нет модуля хостинга — `not_installed`.

**Telegram.** Сначала read-only предпроверка всех выбранных нод (SSH, пины, версия скриптов, SHA-256 встроенного комплекта), один план (`extra` = sha256 комплекта + VERSION), затем параллельные (до 4) воркеры на замороженном снимке предпроверки; недоступная нода — строка `error`, остальные выполняются. Итог — агрегат v1: любая строка `error` → код 1/`remote_failed`; иначе `partial` → 4; иначе `not_installed` (хотя бы на части нод) → 3; иначе успех. `telegram menu` — предпроверка одной ноды и PTY в серверное меню без автозагрузки скриптов (`invalid` с командой `node upload-scripts`), без консоли — `tty_required`.

**Сигналы.** SIGTERM/SIGHUP/SIGQUIT (Windows: закрытие консоли, Ctrl+Break, выход, выключение) восстанавливают консоль из raw mode и завершают процесс с кодом 128+сигнал (Windows — `STATUS_CONTROL_C_EXIT`). Процессный тест `serve_protocol::termination_signals_restore_the_raw_console`: настоящий псевдотерминал (`libc::openpty`, `setsid` + `TIOCSCTTY`), raw mode скрытого ввода пароля, SIGTERM и SIGHUP, проверка `ICANON|ECHO` терминала после выхода. Детерминированный seed ключей существует только под `#[cfg(test)]`.

**Проверка (Linux).** `~/.cargo/bin/cargo build --workspace --locked`, `~/.cargo/bin/cargo test --workspace --locked` — без ошибок: core 228, `protocols_golden` (292 случая), `ssh_wire` 7, `cli_contract` 18, `github_source` 11, `serve_protocol` 5, `state_process` 11, bin 4. Не проверялись: настоящие ноды (скрипты nginx/subscription, telegram, AWG, DNAT), реальные HTTPS-проверки Telegram, параллельные SSH-сессии к настоящим серверам, Windows-консоль в работе (сборка под `x86_64-pc-windows-msvc` проверена RewriteVerification только для типов).

## Шаг 8: терминальное меню (ratatui)

**Один бинарник.** `remote-control/tui` (`essence-rc-tui`) — библиотека без зависимости от `rc-core` (проверяет `remote-control/tui/tests/boundary.rs`: манифест, импорты, отсутствие `main.rs`/`[[bin]]`). `essence-rc` без аргументов при терминальных stdin/stdout вызывает `essence_rc_tui::run_terminal()` в своём процессе; ядро — дочерний `std::env::current_exe()` + `serve --inner` (без поиска в `PATH`), только JSONL v2: запросы `{"id","argv","secrets"?}`, лог-события рендерятся живьём до ответа. Диагностика serve пишется в анонимный временный файл; при сбое старта показывается её хвост. Релизный workflow и `install-essence-rc.sh` собирают и ставят только `essence-rc` — изменений не требуют.

**Сигналы.** Меню перехватывает SIGINT на всё время работы: в меню Ctrl+C (клавиша в raw mode или сигнал ОС) закрывает сессию (EOF serve) и даёт выход 130; во время запроса, редактора или терминальной команды SIGINT игнорируется (serve тоже его игнорирует), а нажатия Ctrl+C, пришедшие во время запроса, отбрасываются. SIGTERM/SIGHUP/SIGQUIT (Windows — события консоли) восстанавливают терминал и завершают процесс 128+N; паника восстанавливает терминал и выходит с 1 без payload.

**Терминальные команды.** `node shell` и `telegram menu` выполняет сам serve-потомок: `serve --inner` подключает `TerminalConsole` к общему управляющему терминалу (Unix `/dev/tty`, Windows `CONIN$`/`CONOUT$`), меню на время запроса приостанавливается (cooked mode, основной экран) и не читает терминал. Так команда идёт внутри уже открытой сессии; прежний одноразовый дочерний `essence-rc` открывал вторую сессию и при GitHub-источнике получал `locked`. Публичный `serve` консоль не подключает — `tty_required`. `telegram menu` скрипты не загружает: ответ `invalid{state}` экран превращает в отдельную подтверждённую `node upload-scripts` (`--force` для повреждённой установки), без автоповтора.

**Экраны** (`system`, `source`, `nodes`, `clients`): паритет дерева C.2 с v1 `remote-control/tui/*.sh` на грамматике v2 (`subscription`, `--name` у `conn`/`awg`/`telegram`/`subscription`). Общие правила: рамка 68 + разделители без пустых секций (кадр без содержимого — без разделителя), буквенные клавиши в обоих регистрах, неизвестное — «Неверный выбор.», `0` — Назад/Отмена; стрелки дополняют ключи (`app::Picker`: ↑/↓ — подсветка, Enter/→ — выбор, Esc/← — `0`, Пробел — переключение в мультивыборе; режим кадра — `ui::Mode`); подтверждение — план из `confirmation_required`, один y/N (по умолчанию N), повтор с `--yes --plan-token`, `plan_changed` показывается заново не более двух раз (как v1); коды решений GitHub → флаги в `confirm::decision_flag`; обработчик кодов ноды; секреты только скрытым вводом и полем `secrets`. serve v2 не журналирует текст ошибки, поэтому `error.message` неудачного ответа показывается один раз центрально (кроме `confirmation_required`, `plan_changed`, `*_required`). Редактор шаблонов — `$VISUAL`/`$EDITOR`/`nano`/`vi` (Windows — `notepad`) на приватном временном файле с проверкой «без изменений», импорт через план.

**Отклонения.** URL подписки — обычный текст без OSC8 (ratatui вырезает управляющие символы; терминалы распознают ссылку сами). Вывод curl/JSON/QR и содержимое шаблона показываются внутри read-only рамки. Сбой чтения экрана предлагает «Повторить».

**Проверка (Linux).** `~/.cargo/bin/cargo build --workspace --locked`, `~/.cargo/bin/cargo test --workspace --locked` — без ошибок: core 233, `protocols_golden` 1, `ssh_wire` 7, `ssh_e2e` 1 (без `E2E_SSH` — пропуск), `cli_contract` 18, `github_source` 11, `serve_protocol` 5, `state_process` 11, bin 4, **tui 98** (TestBackend-рамки и логика экранов против скриптового serve: argv по клавишам в обоих регистрах, подтверждения, код → флаг, пустые/ошибочные состояния, отсутствие секретов в argv/кадрах), **boundary 2**, **`tui_e2e` 7** (настоящий `essence-rc` на Linux PTY: первый запуск → `source init-local` → группа → генерация → выход; коды запуска как в v1: «Выход» первого запуска — 0, ядро не стартовало или сессия не открыта — 1; Ctrl+C и SIGINT ОС в меню → 130 с восстановленным терминалом и снятой блокировкой; `serve --inner` пропускает `node shell`/`telegram menu` через терминал внутри своей сессии, публичный `serve` — `tty_required`; сценарный обход разделов против настоящего ядра без единого `usage`). `~/.cargo/bin/cargo clippy --workspace --all-targets --locked` — без ошибок (предупреждения стиля, в основном `collapsible_if`). Не проверялись: настоящий PTY-проброс к ноде (`node shell`/`telegram menu` с SSH), внешний редактор и `qrencode` в живом терминале, Windows-консоль (`CONIN$`/`CONOUT$`, notepad), macOS.

## Шаг 10: cutover

Bash-клиент удалён (entrypoint, модули ядра, экраны, установщик и WSL-лаунчер); Cargo workspace переехал из `rs/` в `remote-control/` — клиент снова живёт в своём каталоге: `remote-control/{core,bin,tui}`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`. Встроенные шаблоны — `core/templates/`. Ядро встраивает только `core/templates`, `setup-essence/`, `common/`, `VERSION` (и в тестах `tests/fixtures/sample_config.json`); `remote-control/.remote-data/` (данные прежней Bash-версии) игнорируется git и ни во что не встраивается, `remote-control/target/` игнорируется. Серверный релизный архив (`tests/ci/build_release_tarball.sh`) по-прежнему отклоняет любой `remote-control/` — исходники клиента в нём не поставляются. `bash tests/run_tests.sh --all` запускает серверные BATS и `cargo test --workspace --locked`.

Правки пользователя перенесены: цвет только у ключа пункта (`common/common.sh::menu_item`, в Rust — `ui::View`, тест `ui::tests::item_colour_covers_only_the_key`), группировка корневого меню цветом раздела (`system::dashboard_view`, тест цветов дашборда), правила в скилле `essence-menus` и в `docs/remote-control.md`; `tests/unit/menu_ui.bats` остался серверным тестом примитивов `common/common.sh`.

**Репозиторий Bash-версии и отзывчивость меню.** Репозиторий `essence-remote-control-config`, оставшийся от Bash 1.x (plain-раскладка с `ssh/known_hosts`, снимок формата 2 с минимальной версией 1.1.0), раньше останавливал `source github-connect` на allowlist дерева (`source_failed`, этап «проверка файлов репозитория GitHub»). Теперь любой репозиторий без читаемой конфигурации v2 (посторонние файлы, недопустимое дерево, нет `storage.json`, `github_format_invalid`; снимок 1.x — `github_format_invalid`, не `newer`) — решение `target_replace_required{repo,tracked_files,reason}`; с `--replace-target` (план с числом удаляемых файлов) файлы удаляются коммитом поверх истории и публикуется конфигурация устройства. Меню: мастер спрашивает про замену с причиной; все строки (рамка, журнал, строка ввода) переносятся по словам в ширине кадра; `ProcessClient` читает stdout ядра в отдельном потоке, и каждый запрос через `Context::request` сразу рисует строку состояния со спиннером и временем (`app::activity`), обновляемую каждые 100 мс и событиями журнала. Тесты: `github_source::connect_replaces_foreign_v1_repository`, `github_source::tui_wizard_walks_github_paths` (настоящие экраны и `serve --inner` против локального bare-репозитория), `ui::tests::long_russian_error_wraps_fully_inside_the_frame_width`, `app::tests::status_line_is_drawn_before_a_slow_reply_and_animates`, `serve::tests::slow_reply_ticks_while_in_flight`.
