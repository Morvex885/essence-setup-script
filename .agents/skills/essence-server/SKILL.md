# Essence server

## Когда применять

Любое изменение того, что оказывается на сервере: новый протокол или роль ноды, формат отрендеренного файла, этап исполнителя, порты, UFW, сертификаты, `node apply`. Правила самих команд (каталог, коды, план) — скилл `essence-commands`, экраны — `essence-menus` и `essence-web`. Сервер настраивается только из RC: RC хранит желаемое состояние, сам рендерит все файлы ноды и применяет их транзакционно; на ноде нет меню и бинарника Essence, после применения VPN работает без RC.

## Карта файлов

Пути Rust — от `remote-control/core/src/`.

## Инварианты

- **Рендер чистый и детерминированный.** `render.rs` не ходит в сеть и в каталог данных; одинаковая конфигурация даёт одинаковые файлы и `digest`. Без `secrets` содержимое файлов пустое, но `digest`, `lines`, `ports`, `spec` те же — так считаются статус и план.
- **Дайджест.** Нода `applied`, когда `desired(...).digest == applied.digest`, иначе `pending`. Всё, от чего зависят файлы ноды, входит в `Layout::digest` (профиль без имени, адрес, домен, порты, `params`, пользователи листенеров, пиры AWG, каскады, хост подписок, Telegram, репозиторий и ревизия tproxy-server). Изменение формата файлов при той же конфигурации — `RENDER_REVISION += 1` (сейчас 8).
- **Секреты** (`reality-key`, `awg-key`, `warp-key`, `telegram-secret`, `telegram-tag`) читаются только при сборке каталога операции (`apply::node_secrets` внутри `claim`); нет секрета — `missing_secret` этой ноды. В план, `lines`, журнал и `extra` они не попадают. В хранилище GitHub ключ, который устройство не расшифровывает, переносится из прежнего снимка (`vault::carry_unreadable`), а не теряется.
- **Только `node apply` меняет ноду.** Команды модели к ноде не подключаются. Исключения: регистрация WARP (в `node apply` до `claim` и `node warp-reregister`), `telegram status|restart|diagnostics`, публикация подписок. Публикация проверяет не статус ноды, а роль: `render::sub_role_applied` — в `applied.files` (и в `operation.files`, если операция идёт) есть отметка webroot хоста и vhost `essence-sub` с тем хэшем, который рендерится сейчас; другие неприменённые изменения ноды подпискам не мешают, иначе `not_installed`.
- **Сгенерированное не меняется.** `ensure_generated` только дописывает недостающее (параметры ноды, приватные ключи в `SecretStore`, учётные данные клиентов) и вызывается внутри `Session::mutate` команд, меняющих профиль, ноду, клиентов, каскады, Telegram. Единственное исключение — порт перехвата AWG: `tproxy_port` (10000–60000) выбирается вне портов ноды (`taken_ports`: порты профиля с переопределениями, 443, SSH, `RESERVED_PORTS`, порт хоста подписок на этой ноде), и если позже какой-то из них занял его, `ensure_generated` выбирает новый.
- **Порт протокола** — `node.ports[ключ]`, иначе порт профиля; `vless-tcp` всегда 443. Порты листенеров не совпадают с SSH ноды и портом перехвата AWG (`check_ports` → `invalid` с `port`); профили не берут `RESERVED_PORTS`.
- **Фронт 443** (`render::front`) — от действующих портов, а не от одного факта включения Reality:

| `Front` | Условие | 443 слушает | vhosts (сайт, подписки, Telegram) |
|---|---|---|---|
| `SelfSteal` | Reality-листенер на 443, `reality_mode = self-steal` | mihomo `0.0.0.0:443`, `dest 127.0.0.1:8443` | `127.0.0.1:8443` по `server_name` |
| `Stream` | Reality-листенер на 443, `sni`, на ноде роль на 443 (Telegram или хост подписок с портом 443) | nginx `stream` с `ssl_preread` (`modules-enabled/90-essence-stream.conf`) | подписки — 8445, Telegram — 8446, остальное → mihomo `127.0.0.1:8444` |
| `Bare` | Reality-листенер на 443, `sni`, ролей на 443 нет | mihomo `0.0.0.0:443`, `dest <sni_domain>:443` | на 443 нет (хост подписок — только на своём порту) |
| `Free` | Ни один Reality-листенер не на 443 | nginx напрямую (`443` и `[::]:443`), если есть сайт или роль; иначе никто | на 443 напрямую; self-steal Reality на другом порту берёт `dest 127.0.0.1:443` |

  Reality-транспорты — `vless_tcp`, `vless_xhttp` с топологией `reality`, `vless_grpc`. Сайт ноды (её домен) нужен, если `reality_mode = self-steal` и включён Reality-транспорт, XHTTP через nginx или Hysteria2 (нет домена — `domain_required`).
- **Внутренние порты** (`server/ports.rs`): `SITE_PORT 8443`, `REALITY_INNER_PORT 8444`, `SUB_INNER_PORT 8445`, `TG_INNER_PORT 8446`, `XHTTP_NGINX_PORT 8447`; зарезервированы ещё 9090, 1053, 2398, 8080, 8081, 8888. `Layout::check_ports` сверяет с SSH-портом ноды все TCP-порты: листенеры, 443, сайт, vhost хоста подписок и vhost Telegram (`telegram_port`: 8443 за Self-Steal, 8446 за stream, иначе 443).
- **Домены** сравниваются без учёта регистра (`eq_ignore_ascii_case`): домен роли не совпадает с доменом ноды и других ролей.
- **Маршрутизация mihomo.** Каждый листенер идёт через sub-rule, а не прямо в `outbound`: `rule: essence-in` (`INBOUND_RULE`), листенер с входными каскадами — `rule: <marker>-shared`. Каждая sub-rule начинается с отказов `Layout::inbound_rejects`: `INBOUND_REJECT` (loopback, link-local, частные сети IPv4/IPv6) и собственный адрес ноды (`IP-CIDR,<ip>/32` или `IP-CIDR6,<ip>/128`: `DIRECT` дошёл бы до него через `lo` в обход файрвола) — все строки `…,REJECT` без `no-resolve`; затем `IN-USER,<клиент>--<C>,<C>-outbound` для каскадов и `MATCH,outbound`. AmneziaWG приходит через TPROXY в листенер `awg-tproxy` (`type: tproxy`, `0.0.0.0:<params.awg.tproxy_port>`, `udp: true`, `rule: essence-in`), а не через верхнеуровневый `tproxy-port`, чтобы пройти те же запреты.
- **Отказы — не граница безопасности.** Они останавливают IP и имена с постоянными записями, но не DNS rebinding: mihomo резолвит домен для правил, а `DIRECT` резолвит его заново при соединении, так что домен с TTL 0 проходит проверку с внешним адресом и соединяется с loopback, частной сетью или адресом метаданных. `IPAddressDeny=` или фильтра исходящих для mihomo нет. Не описывать отказы как полную защиту и не полагаться на них для служб ноды на loopback/частных адресах; настоящая граница — sandbox systemd или фильтр исходящих (их добавление — отдельное изменение рендера).
- **AmneziaWG.** `awg0.conf` рендерится целиком: `[Interface]` и по блоку `# peer:` на пира (`awg::expected_peers`). Пиры изолированы: `PostUp` вставляет `iptables -I FORWARD -i %i -o %i -j DROP` (снимается в `PostDown`), трафик клиентов идёт в TPROXY, мимо него — только адрес самого сервера в подсети `10.10.0.0/16`, loopback и multicast.
- **WARP.** Регистрация — сценарий `warp::REGISTER` через `exec` с ключом WARP+ в stdin; на ноде сценарий вписывает его строкой `license_key` в файл аккаунта `wgcf-account.toml` (0600 под `umask 077`) и вызывает `wgcf update`; не argv и не окружение; неудача возвращает прежний файл (копия `.prev`), а если и это не вышло — сценарий падает, оставив копию. Аккаунт хранится в RC (`params.warp`, секрет `warp-key`); `node show|list .warp` — `off` (WARP выключен в профиле), `none` (не зарегистрирован), `free`, `plus`.
- **Свои файлы и чужие.** Пишутся только пути `paths::managed_file` (в исполнителе — `managed_path`; новые пути добавляются в оба места). Сайты nginx начинаются строкой `# Essence site <имя>` — без неё (или ссылка `sites-enabled/<имя>` не на `sites-available/<имя>`) исполнитель путь из `remove.list` пропускает, а путь из `files.list` не перезаписывает (`replaceable`: чужой сайт с тем же именем — сбой `config` до изменений). Отметки webroot: `.essence-site` — сайт-заглушка уже скачан (этап `site` его не трогает); `.essence-sub`, `.essence-telegram` — пустые файлы роли в `applied.files` (по ним рендер знает, чей сертификат снимать при переносе роли), в `config` не удаляются; `cleanup` снимает сертификат из `RELEASE_CERTS` и удаляет webroot, только если в нём есть одна из трёх отметок.
- **`nginx.conf` не редактируется**: лимиты — `conf.d/essence-sub-limit.conf`, сайты — `sites-available` + ссылка, stream — `modules-enabled/90-essence-stream.conf`.
- **Исполнитель не задаёт вопросов** (`exec </dev/null`), не вызывает `error` из `common.sh` (он делает `exit 1` мимо статуса), все абсолютные пути — через `$R` (`${ESSENCE_NODE_ROOT:-}`).
- **Транзакция — от `config` до `committed`.** Всё, что не откатывается (пакеты, сайт, сертификаты, сборка компонентов в `<фича>_prepare`), делается до неё и только добавляет; этап `mihomo` только скачивает бинарник в `<op>/mihomo.new`. `tx_open` (начало `config`) запоминает в `TX_ACTIVE` работавшие mihomo и nginx. В `config`: `adopt_feature_leftovers` (см. ниже), резервные копии всех путей и при новой версии — бинарника mihomo (`<op>/backup`, `.absent`), установка файлов, `tx_deactivate` — `<фича>_deactivate` для каждой фичи `REMOVE_FEATURES`, пока её файлы ещё на месте (остановка служб, `awg-quick down`, `disable` требуют конфиг и юнит; снятые копятся в строке `TX_DEACTIVATED` «фича »), удаление `remove.list`, `install_mihomo`, `sysctl --system`, `mihomo -t`, `nginx -t`, `daemon-reload`, `stop mihomo` → nginx `restart`/`reload` → `start mihomo` → `is-active`, все порты `LISTEN_TCP` в `ss -Htln` (до 10 с), проверка 200 сайта (`SITE_REQUIRE_200`), `<фича>_activate`. Транзакция остаётся открытой через `firewall` (добавленные и снятые свои правила — `FW_ADDED`/`FW_DELETED`) и `stage_cleanup` (только проверка `RELEASE_CERTS`) и закрывается записью `result=committed` в конце `apply.sh`. Сбой или сигнал до неё — `tx_rollback`: файлы и бинарник mihomo (`tx_restore_files`), UFW и учёт (`tx_restore_firewall`), тот же перезапуск, `sysctl --system`, `<фича>_rollback` для `FEATURES` и `TX_DEACTIVATED`, проверка, что службы `TX_ACTIVE` снова работают; всё получилось — `result=rolled_back`, иначе `result=rollback_failed` (`backup/` остаётся). `teardown` тоже вызывает `tx_deactivate` до удаления файлов. Необратимое — `<фича>_remove` (файлы, каталоги, учётные записи), освобождение сертификатов и webroot, удаление старых операций (кроме `rollback_failed`) и исполнителей — только в `cleanup_committed` после записи `committed`; её сбой — предупреждение, итог не меняется. Новое необратимое действие — туда же, не в этапы.
- **Откат фичи трогает её, только если транзакция её трогала.** `<фича>_rollback`: фича снималась в этой операции — службы снова включаются, если после возврата файлов роль на месте (иначе остаются выключенными); первая установка (копия `.absent`) — службы останавливаются и выключаются; файл фичи изменён транзакцией (`cmp` с копией) — перезапуск с прежним; откат по чужой причине (`mihomo -t`, nginx, другая фича) работающую фичу не трогает.
- **Остатки незафиксированных фич.** `<фича>_prepare`, начиная ставить компоненты, ставит метку `/root/essence-node/features/<фича>`, `<фича>_remove` её снимает (сейчас так делает `telegram`). `adopt_feature_leftovers` в начале `config`: метка фичи, которой нет ни в `FEATURES`, ни в `REMOVE_FEATURES` (сбой `prepare` или откат до фиксации роли), добавляет фичу в `REMOVE_FEATURES` — она проходит обычный путь `deactivate` → `remove`.
- **Учётные записи Telegram.** `_tg_ensure_user` создаёт `mtproxy`/`tproxy` (`useradd --system`, `nologin`) и записывает созданные в `/root/essence-node/telegram-users`; существующая учётная запись принимается, только если она системная (UID ≤ `SYS_UID_MAX`) и без входа, иначе сбой `prepare`. `telegram_remove` удаляет только записанных в `telegram-users` (и Go из `telegram-go`), чужие не трогает.
- **UFW**: без `ufw --force reset`; правила этой операции откатываются вместе с транзакцией; выключенный включается с разрешёнными `SSH_PORTS`; свои правила учитываются в `/root/essence-node/ufw-rules` (учёт пишется после каждого изменения), правило, добавленное до нас администратором, не учитывается и не удаляется.
- **Прогресс.** Процент операции только растёт: `progress_plan` делит 0–100 между этапами по весам `_progress_weights` (`packages` 20, с nginx 25; `certificate` 4 + 6 на сертификат; `prepare` 2, +1 за сертификат Hysteria2, плюс `progress_feature_weight` каждой фичи — `awg` 30, `telegram` 35, прочие 1; `mihomo` 4, `site` с загрузкой 4, `config` 4, остальные 1; `teardown` — `config` 6, `firewall` 2, `cleanup` 2). `stage` сам ставит диапазон этапа; шаг выбирает долю этапа `progress_span <от> <до>` и движется по ней `progress_in <процент>`; `progress_detail "…"` — текущее действие (без управляющих символов, до 120 символов, без секретов: имена пакетов, доменов, постоянные тексты). Проценты пишутся не чаще раза в секунду (секунда — по `$SECONDS`: `progress.sh` совместим с Bash 3.2, без `printf '%(…)T'`), смена действия — сразу. Пакеты — только `agent_apt <от> <до> <команда apt-get> …` (после `agent_apt_wait`): apt идёт в фоне, его `APT::Status-Fd` — приватный FIFO, читатель в том же процессе (процент apt, загрузка — первые 30 % доли, ведёт долю шага) кончает на EOF или через секунду тишины после выхода apt, так что потомки apt, унаследовавшие дескриптор, шаг не держат; вывод — в журнал операции. Новая долгая фича получает вес в `progress_feature_weight`. RC показывает это живой строкой (`Session::progress` → событие `progress`), журнал получает только смену этапа и сбои.
- **Подсказка сбоя.** Исполнитель, распознавший причину, которую чинит пользователь, ставит `HINT=<id>` (`hint=` в `status`); текст — `apply::hint_text` (сейчас `kernel_headers`: обновить ядро и перезагрузить сервер), RC дописывает его в `message` сбоя.
- **Отвязанный запуск.** RC запускает исполнитель юнитом `essence-apply-<op_id>` (`systemd-run --collect`) и только опрашивает; `flock` на `/root/essence-node/lock` не даёт двух операций на ноде, `node.operation` — в RC. `timeout` (10 мин без связи, 60 мин всего) оставляет `operation`: следующий `node apply` продолжает опрос.

## Добавить протокол или роль

1. Модель: поле `Profile` (или запись роли в `Config`) + проверка в `validate`; для портов — ключ `NODE_PORT_KEYS`, если порт переопределяется на ноде.
2. Новые ключи и параметры — в `ensure_generated` (приватное — в `SecretStore` с новым суффиксом `validation::NODE_SECRET_SUFFIXES`, публичное — в `NodeParams`); секрет — в `NodeSecrets`, `apply::node_secrets`, перенос хранилища GitHub, удаление в `nodes/delete.rs`.
3. Рендер: файлы (`files`, путь в `paths.rs` и `managed_path`), строки `spec` (новые ключи — и умолчание `: "${KEY:=}"` в `apply.sh`), `LISTEN_TCP`, правила `rules()` → `UFW_RULES`, сокеты службы в `listen`, строки плана `lines`, при необходимости `CERTS`/`DNS_DOMAINS`/`RELEASE_CERTS`; учесть `Front`, `check_ports` и `taken_ports` (порт перехвата AWG).
4. Вход в `digest` — всё, от чего зависят файлы; при смене формата для прежней конфигурации — `RENDER_REVISION`.
5. Системные действия — `node-agent/steps/<фича>.sh` с `<фича>_prepare|activate|rollback|deactivate|remove` (идемпотентно, без вопросов; `deactivate` — остановка до удаления файлов, `rollback` — по правилу «трогает, только если транзакция трогала», метка `features/<фича>` в `prepare`, если частичная установка должна сниматься) и фича в `FEATURES`/`REMOVE_FEATURES` (`teardown` перечисляет все фичи); пакеты — `agent_apt`, действия — `progress_detail`, вес фичи в `prepare` — `progress_feature_weight`.
6. Клиентская сторона — `client_section` (билдеры `protocols/*`) и `proxies` (имя подключения); `generate` и `conn sync` берут их оттуда.
7. Тесты рендера (`server/render/tests.rs`) и BATS (`tests/unit/node_agent.bats`), затем команды и экраны.

## Форматы каталога операции

Каталог на ноде — `/root/essence-node/ops/<op_id>/` (`op_id` — 32 hex), загружается `upload_private` (0700/0600) при каждом применении; исполнитель — `/root/essence-node/agent/<agent_sha>/`, загружается, только если проба не подтвердила `sha256sum -c --quiet MANIFEST`.

- `MANIFEST` — строки `<sha256>  <относительный путь>` (формат `sha256sum`), отсортированы: `apply.sh`, `steps/*.sh` (включая `progress.sh`), `common/common.sh`, `common/cert.sh`; `agent_sha` — SHA-256 текста `MANIFEST`. `apply.sh` подключает только этапы, перечисленные в нём.
- `spec.sh` — строки `KEY='значение'` (экранирование `nodes::sh_quote`), только `source`. Ключи: `OP_ID`, `OP_MODE` (`apply|teardown`), `SSH_PORTS` (порт подключения RC и порт sshd из `$SSH_CONNECTION`, через пробел), `LISTEN_TCP` (TCP-порты, которые обязаны слушаться после `config`), `MIHOMO_VERSION`, `NGINX`, `NGINX_STREAM`, `SITE_NAME`, `SITE_SOURCE`, `SITE_REQUIRE_200`, `CERTS` и `RELEASE_CERTS` (`имя:/var/www/имя` через пробел), `ACME_EMAIL`, `DNS_DOMAINS`, `HY2_CERT`, `HY2_CN`, `UFW_RULES` (`443/tcp 51820/udp`), `FEATURES`, `REMOVE_FEATURES` (из `awg sub telegram`; исполнитель дописывает остатки через `adopt_feature_leftovers`), `AWG_PORT`, `WARP`, `SUB_HOST`, `TG_HOST`, `TG_REPO`, `TG_REVISION`, `TG_GO_VERSION`, `TG_GO_SHA256` (`TG_*` — только при роли Telegram, иначе пусто). `teardown` передаёт только `OP_MODE`, `SSH_PORTS`, `UFW_RULES` (пусто), `RELEASE_CERTS`, `FEATURES`, `REMOVE_FEATURES`, `WARP=false`.
- `files.list` — строки `<mode> <owner> <group> <абсолютный путь>`; `mode` — 4 восьмеричные цифры или `link` (файл в `files/` содержит цель, `ln -sfn`). Содержимое — `files/<путь без ведущего />`.
- `remove.list` — абсолютные пути (файл, ссылка или каталог — рекурсивно); только управляемые, свои сайты — по отметке.
- `status` — `KEY=value`, запись атомарна (tmp + `mv`, `write_status`): `stage=<этап>`, `progress=<0–100>`, `detail=<текущее действие>` (если есть), итог `result=committed|rolled_back|rollback_failed|failed`, при неуспехе `error=<этап>` или `error=locked`, `hint=<id>` (если исполнитель знает, что делать пользователю). RC перед ним читает `unit=` (`systemctl is-active essence-apply-<op_id>`). Журнал — `<op>/log`; после итога исполнитель удаляет `files/`, `mihomo.new` и (кроме `rollback_failed`) `backup/`. RC: `committed` → `applied`; `rollback_failed` или юнит исчез без `result=` — незавершённая попытка (`apply::End::Incomplete`): файлы и порты операции добавляются к `applied` под `render::incomplete_digest()` (нода `pending`, порты не `port_busy`, хэши не расхождения); иной сбой — `operation` снимается.

Этапы `apply`: `packages` → `system` → `mihomo` → `dns` → `site` → `certificate` → `prepare` → `config` → `firewall` → `cleanup`; `teardown`: `config` → `firewall` (пустой список) → `cleanup`. Подписи этапов для журнала и отчётов — `apply::stage_label` (продублированы в TUI и вебе).

## Проверка

- Рендер — unit-тесты `server/render/tests.rs` (`desired`/`spec`/`content`: каждая топология `Front`, роли, каскады, AWG, WARP, IPv6, удаления) и `server/{cascade,warp}/tests.rs`; разбор YAML вместо сравнения строк там, где важна структура.
- `node apply` — `server/apply/tests.rs` на `FakeTransport` (`nodes::testing`, `tokio::time::pause`, `NEXT_OP_ID`): без `--yes` ни одного `upload`, откат, `rollback_failed` и остановка без результата (файлы и порты попытки остаются своими), обрыв при опросе и переподключение, повтор подключения пробы, живая строка (`nodes::testing::session_live`), подсказка `hint`, возобновление, две ноды с одной недоступной, расхождение в плане, `plan_changed`.
- Исполнитель — `tests/unit/node_agent.bats` и `telegram.bats`: копия `node-agent/` и `common/` в каталог теста, заглушки (`apt-get`, `systemctl`, `ufw`, `nginx`, `ss`, `mihomo` …) через `PATH`, корень ноды — `ESSENCE_NODE_ROOT`; только Linux и Bash 4+ (`require_executor_env` иначе пропускает); `bash -n` каждого изменённого `.sh`.
- Настоящие mihomo и nginx — job `render-check`: `ESSENCE_RENDER_DUMP=<dir> cargo test -p rc-core --lib dump_representative_renders`, затем `sudo tests/ci/validate_render.sh <dir> <mihomo>`. Новая топология или роль — добавить её в `dump_representative_renders`.
- `cd remote-control && cargo test --workspace --locked`, `bash tests/run_tests.sh --all`.
- Живая VPS (Debian 12/13, Ubuntu 22.04/24.04/26.04 с systemd — `server::os::SUPPORTED_OS`) для изменений пакетов, сертификатов, nginx, mihomo, AWG, WARP, Telegram: первое применение, повтор без изменений (`unchanged`), правка вручную на сервере (расхождение в плане), откат, `node delete --scope server`.
