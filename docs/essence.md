# Essence Setup — серверный скрипт

Устанавливается на VPS-сервер. Настраивает прокси-протоколы, VPN-туннели, firewall, TLS-сертификаты и HTTPS-хостинг подписок для клиентов.

## Меню

| Пункт | Описание |
|---|---|
| **b) Базовая установка** | Mihomo, systemd, UFW, BBR; перед сбросом всех правил UFW — обзор и подтверждение |
| **v) VLESS Reality** | VLESS с XTLS-Reality (TCP, xHTTP, gRPC), Self-Steal / SNI, nginx + acme.sh |
| **h) Hysteria2** | QUIC, опционально с obfs salamander |
| **a) AmneziaWG 3.1** | VPN-туннели с автоматическим созданием клиентов |
| **t) Telegram Proxy** | Web Proxy и MTProto Proxy |
| **i) IPv6** | Включение / отключение IPv6 |
| **w) WARP** | Cloudflare WARP как исходящий прокси |
| **c) Каскады** | DNAT или прокси через входные подключения Mihomo |
| **s) Хостинг подписок** | HTTPS-хостинг через nginx (`/sub/<token>`) |
| **k) Показать клиентский конфиг** | Готовые данные подключения |
| **m) Показать серверный конфиг mihomo** | Текущий YAML Mihomo |
| **u) Обновить скрипты** | Обновление до последней версии |
| **x) Удалить всё установленное** | Обзор всех компонентов, выбор судьбы SSH и одно подтверждение |
| **0) Выход** | Завершить сессию |

Буквы принимаются в обоих регистрах. Старые числовые клавиши 1–10 удалены.
Публичные IPv4/IPv6 определяются в фоне один раз за сессию; меню не ждёт сеть.
Замена каскада происходит только после ввода новых параметров и подтверждения:
отмена сохраняет прежнюю конфигурацию. Пароли и UUID не показываются в обзоре
перед установкой; готовые данные подключения печатаются после успеха.

Удаление через `x` перечисляет Mihomo, AmneziaWG, WARP, сайты nginx, сертификаты,
хостинг подписок, Telegram Proxy, acme.sh, сетевые настройки и судьбу UFW/SSH.
Пакеты nginx и AmneziaWG не удаляются. Для автоматизации remote-control использует
`bash setup-essence.sh uninstall --force`: команда разрушительная, работает без
вопросов и сохраняет текущий порт и способ входа SSH.

Все меню перерисовывают полный framed-экран через общие `box_*` и `menu_item`.
`0` и EOF возвращают в предыдущее меню; Enter использует default только в
приглашениях, где он явно указан. Неверный ввод остаётся на текущем экране.
Операционные ошибки показываются как предупреждения и не закрывают главный
entrypoint — действие можно повторить из того же меню.

### Общий lifecycle сертификатов ACME

VLESS с собственным TLS-сайтом, хостинг подписок и Web Proxy используют
один lifecycle из `common/cert.sh`. При установке сначала переиспользуется
пригодная установленная пара с регистрацией acme.sh, затем — сохранённый архив
`~/.acme.sh/<hostname>/` (RSA) или `<hostname>_ecc/` (ECC). Восстановление архива
не создаёт новый заказ Let's Encrypt.

Пригодность проверяется OpenSSL ≥1.1.1: SAN нужного DNS/IP, доверенная цепочка,
совпадение приватного ключа и остаток срока строго больше 24 часов, в том числе
для shortlived IP-сертификатов. Проверка использует системный CA bundle
`/etc/ssl/certs/ca-certificates.crt` либо явно заданный `SSL_CERT_FILE`.
Сертификат без регистрации заменяется обычным ACME-заказом для автоматического
продления. Отсутствие OpenSSL/trust store или повреждённая регистрация —
ошибка, а не повод для выдачи.

Обычная выдача не использует `--force`. Один принудительный запрос разрешён
только после ACME skip (код 2), если пригодных копий нет. Ошибки CA, лимитов,
DNS, challenge и сети не запускают принудительный повтор.

Постоянный nginx site `essence-acme-<hostname>` с маркером
`# Essence ACME challenge` обслуживает HTTP-01 и сохраняет общий webroot,
пока сертификатом пользуется другая фича. TCP/80 открывается на время выдачи
и штатного продления; Telegram восстанавливает исходное правило UFW.
Не удаляйте общий route вручную, пока автоматическое продление активно.

Удаление отдельной фичи сохраняет установленную пару и продление при наличии
другого nginx TLS-потребителя. После последнего потребителя локальная пара,
общий route и его webroot удаляются; registration становится `.conf.removed`,
но сертификат, ключ и account в acme.sh остаются. Повторная установка
восстанавливает пригодный архив и возобновляет продление без нового заказа.
Полный подтверждённый uninstall, напротив, удаляет и архив acme.sh.
Удаление не отзывает сертификаты и не сбрасывает лимиты CA.
Удаление Web Proxy совместимо с Bash 3.2 и `set -u`, в том числе когда
дополнительных shared webroots нет; основные entrypoints не включают strict mode.
Self-signed сертификат Hysteria2 к этому lifecycle не относится.


### Telegram Proxy — способы доступа и общая служба

Web Proxy и MTProto Proxy — два способа доступа к одной службе MTProxy,
с общим секретом и необязательным Спонсорским тегом из @MTProxybot.
Web Proxy переносит трафик через HTTPS/WebSocket к локальной службе;
прямой публичный доступ MTProto для него не требуется. Служба устанавливается
автоматически, сохраняется пока включён хотя бы один способ и удаляется
после отключения последнего. Web Proxy требует совместимого клиента Telegram;
обычная ссылка `t.me/proxy` доступна только у MTProto Proxy.

| Часть | Порты | Назначение |
|---|---|---|
| **Web Proxy** | Публичный TCP/443 через выбранный TLS frontend, HTTP-01 на TCP/80 | HTTPS/WebSocket-доступ |
| **MTProto Proxy** | Публичный TCP/2398, только при включении | Прямой клиентский доступ |
| **Служба MTProxy** | Локальный TCP/2398 | Общая служба обоих способов доступа |
| **Локальный relay** | Локальные TCP/8080, TCP/8081 | Web Proxy и диагностические endpoints |
| **Статистика MTProxy** | Локальный TCP/8888 | Публичный доступ закрыт |

Владение TLS listeners определяется topology, а не наличием AAAA-записи:

| Topology | TLS listeners WEB nginx | Публичный TCP/443 |
|---|---|---|
| `direct` | `443` и `[::]:443 ipv6only=on` | nginx |
| `self-steal` | Только `127.0.0.1:8443` | mihomo; передаёт WEB SNI в локальный nginx |
| `sni` | Только `127.0.0.1:8446` | Существующий SNI frontend |

`TELEGRAM_WEB_IPV6=true` сохраняется для IPv6-доступа через внешний frontend:
в `self-steal`/`sni` это не разрешает nginx занимать дополнительный публичный
`[::]:443`. REALITY, другие vhosts и SNI stream-конфигурация не меняются.

Web Proxy требует доменное имя с DNS A-записью на публичный IPv4 и email для Let's Encrypt.
После согласия оператора установка сначала поднимает и проверяет службу MTProxy:
неисправная управляемая зависимость восстанавливается с сохранением секрета и тега.
Восстановление может прервать действующие подключения. Исправная служба с
каноническим unit не пересобирается и не перезапускается. Только затем готовятся
decoy-сайт и relay, выпускается сертификат и проверяется nginx.
Ошибка службы останавливает установку до сборки/ACME/записи state; отмена decoy
или ошибка последующих этапов откатывает файлы, users, units, nginx, nftables и UFW.

После успешного `nginx -t` и reload установщик дополнительно ждёт TLS для WEB
hostname через loopback на порту выбранной topology, до изменения firewall и
записи нового installed state. Проверка использует SNI, стандартное доверие CA
и проверку hostname; публичный DNS, proxy и пользовательский curlrc не участвуют.
Ошибка TLS отвергает установку и запускает штатный rollback вместо сообщения
об успехе. Сам по себе успешный reload не доказывает применение конфигурации:
при конфликте listeners nginx может продолжить обслуживать старую.

Для уже установленного Web Proxy с готовыми relay/MTProxy/timer успешный no-op также
требует одной локальной TLS-пробы. Если TLS недоступен, команда возвращает ошибку
без полной переустановки, prompt, ACME, reload или записи state/secret.
Это подтверждает TLS-вход для hostname, но не все директивы nginx, публичную
маршрутизацию или клиентский WebSocket/MTProxy-трафик. HTTP status, включая 503,
не является критерием этой TLS-пробы; она не следует redirect.

MTProto Proxy не требует доменного имени и сертификата, но межсетевой экран
провайдера должен разрешать TCP/2398 и запрещать TCP/8888. При одном Web Proxy
внешний TCP/2398 закрыт. Способы отключаются независимо: отключение одного
сохраняет другой и службу MTProxy. `remove-all --force` удаляет оба способа
и общие артефакты только после явного вызова.

Локальный CLI:

```text
telegram-proxy menu
telegram-proxy web install|remove [--force]
telegram-proxy web restart|update
telegram-proxy mtproto install|remove [--force]
telegram-proxy mtproto refresh-ip
telegram-proxy backend restart
telegram-proxy status [--json]
telegram-proxy connection
telegram-proxy diagnostics
telegram-proxy rotate-secret [--force]
telegram-proxy tag show|set
telegram-proxy tag clear [--force]
telegram-proxy remove-all --force
```

`web restart` перезапускает только Web Proxy. `backend restart` перезапускает
службу MTProxy для любого включённого способа доступа, проверяет локальный
listener и готовность Web Proxy, если он включён. Перезапуск разрывает действующие
подключения, но не задаёт вопросов ни в меню, ни в CLI.
У restart нет `--force`/`--json`; старая команда `mtproto restart` удалена.

`status --json` — один JSON-объект без secret и tag: код `0` означает
валидное установленное состояние (не обязательно работающие службы), код `3` —
отсутствие установки с `installed=false`. Некорректный state, остаточные
артефакты или несогласованные env/profiles дают код `1` без фиктивного JSON.
Текстовый статус показывает фактическое состояние служб, проверку работы,
готовность и приём подключений; включённый способ не объявляется исправным
без проверки. Проверки Web Proxy локальные, а не гарантия публичного TLS
или клиентского подключения. После успешной локальной установки, смены секрета
или обновления IP автоматически печатаются общий секрет и ссылки.
`connection` показывает их повторно; `tag show` явно печатает Спонсорский тег.
`--force` у установки и смены секрета подавляет рамку, вопрос и автовывод ссылок;
ошибки и отмена не печатают данные подключения. `web update` и `mtproto refresh-ip`
не принимают `--force`; отсутствие доступной ревизии или публичного IPv4 —
ошибка, а не успешный no-op.
Для WEB выводится только `tg://webproxy?...`: публичный маршрут `t.me/webproxy`
не зарегистрирован. Ссылка требует клиента с поддержкой Web Proxy.
Диагностика скрывает секрет, Спонсорский тег, Authorization и request credentials.
После rotate-secret служба MTProxy перезапускается и проверяется даже при одном
Web Proxy; для него также проверяется новый секрет. При ошибке прежние env/profiles и runtime
возвращаются. Upstream relay собирается только из
зафиксированной ревизии `f7a6acc4d536a787d442fd7df3ba4ebfd728f406`; mutable
ветки не используются.

Проверка systemd expansion на Linux от root из корня checkout (без `sudo`):

```bash
TPROXY_SMOKE_CONFIRM=isolated-unit bash tests/smoke/telegram-proxy-systemd.sh
```

Smoke проверяет настоящий argv для пустого и заданного tag на временных runtime
units с безвредным probe, затем удаляет их. Он не читает production credentials,
не запускает MTProxy/nginx, не меняет firewall и не выпускает сертификат.
Успех argv-smoke не доказывает готовность production backend: после него
выполните штатное включение WEB и проверьте общий backend и WEB readiness в статусе.

#### Адресное nginx-only восстановление WEB

Если reload оставил старую TLS-конфигурацию из-за лишнего публичного listener
в `self-steal`, не запускайте `web install --force`: это затрагивает backend и
сертификаты, а занятые relay-порты могут остановить установку. Для подтверждённого
узла `vm1410146` подготовлена отдельная операторская транзакция
`telegram-web-nginx-repair.sh` (передаётся вместе с исправленным модулем, не входит
в CLI). Запуск — от root в отдельном Bash, с SHA-256 модуля из проверенной поставки:

```bash
bash ./telegram-web-nginx-repair.sh "$EXPECTED_MODULE_SHA256"
```

Доставьте модуль в `~/essence-setup/modules/telegram-proxy.sh`; не получайте
ожидаемый digest из самого файла на узле. Транзакция загружает определения из
`common/common.sh`, `common/cert.sh`, `modules/subscription.sh` и
`modules/telegram-proxy.sh`, но не делает `source setup-essence.sh`:
entrypoint запускает updater/CLI/menu. На этом узле entrypoint расположен
непосредственно в `~/essence-setup/setup-essence.sh`.

До изменений обязательны согласованный state/env/profiles, WEB=true,
hostname=`deweb.p1ng2win.ru`, topology=`self-steal`,
TLS listen=`127.0.0.1:8443`, IPv6=true, обычный WEB site, enabled symlink на него,
читаемые существующие certificate/key и активные nginx/relay/backend.
Остановите параллельное редактирование сайта. В root-only backup сохраняются site
с metadata, target symlink, время и диагностика; candidate строится штатным
renderer. Разрешён только diff с удалением одной строки
`listen [::]:443 ipv6only=on ...;`. Любые другие изменения, включая пользовательские
директивы, требуют отдельного решения; такой файл не перетирается.

Заменяется атомарно только WEB site (0644), symlink не меняется; далее выполняются
`nginx -t`, reload nginx и локальная CA/hostname TLS-проба. При ошибке после замены
выполняется один site-only rollback с прежними metadata; reload восстановленного
файла разрешён только после успешного `nginx -t`. Исходный ненулевой код выхода
сохраняется. Backup остаётся оператору. Возврат старого конфликтного сайта
восстанавливает прежнее состояние, а не исправляет HTTPS. Никаких restart,
ACME или изменений state, secret, REALITY, других vhosts, firewall/DNS нет.

После локального TLS commit отдельно проверьте публичный IPv4 и IPv6 TCP/443
с CA/hostname verification, `ss -ltnp` (публичный443 — mihomo, nginx — loopback8443),
`telegram-proxy status --json` (WEB IPv6=true) и новый интервал nginx error.log:
нет новых `bind() to [::]:443 failed`. Если локальный TLS проходит, а публичный нет,
исследуйте frontend отдельно, без переустановки backend; успешный локальный commit
не откатывается из-за последующей публичной проверки.
Затем подтвердите реальное подключение и обмен трафиком по существующей
`tg://webproxy?...` ссылке в поддерживающем WEB клиенте, сравнив sessions/bytes
в `http://127.0.0.1:8081/metrics` до и после попытки. Рост counters и readyz сами
по себе не заменяют клиентский успех; secret не выводите. Без операторского
выполнения и клиентского подтверждения production-восстановление не доказано.

### VLESS Reality — подменю

| Пункт | Описание |
|---|---|
| **1) Настройка Reality** | Выбор режима (Self-Steal / SNI), домен, сертификат, ключи |
| **2) Добавить TCP** | VLESS TCP с flow xtls-rprx-vision на порту 443 |
| **3) Добавить xHTTP** | VLESS xHTTP — через Reality (порт 443 или кастомный) или через nginx TLS |
| **4) Добавить gRPC** | VLESS gRPC через Reality |
| **d) Удалить транспорт** | Динамический список установленных транспортов |
| **s) Статус** | Показать текущие настройки Reality и установленные транспорты |

#### Режимы Reality

- **Self-Steal** — скрипт маскируется под собственный домен с реальным TLS-сертификатом (acme.sh + Let's Encrypt). Нужен собственный домен с A-записью на сервер.
- **SNI** — трафик маскируется под чужой домен (например, `google.com`). Сертификат запрашивать не нужно, но можно развернуть локальный decoy-сайт.

#### Контакт Let's Encrypt

VLESS с сертификатом, хостинг подписок и Telegram WEB используют один контакт
acme.sh на этой ноде. Enter при первом запуске предлагает случайный адрес;
после установки acme.sh — текущий адрес аккаунта Let's Encrypt. Если контакт
не удалось прочитать, адрес нужно ввести вручную. Смена известного контакта
требует подтверждения и после успешного обновления аккаунта меняет сохранённые
email в Reality и Telegram WEB (если эти компоненты установлены). Настройки
других нод через remote-control не изменяются.

### Hysteria2 — подменю

- **1) Установить** — самоподписанный сертификат, выбор порта, опциональный `obfs salamander` (маскирует QUIC-сигнатуру XOR'ом с общим паролем)
- **2) Удалить**

### AmneziaWG 3.1 — подменю

- **1) Установить / обновить сервер** — интерфейс `awg0` в подсети 10.10.8.0/24 с официальными параметрами AmneziaWG 3.1: J/S/H, Header Protection, content padding, randomized timings, Random Trailers и Disable Cookies
- **2) Добавить клиента (peer)** — перевыпускает native-конфиг, QR-код и Mihomo-прокси с теми же параметрами 3.1
- **3) Удалить клиента**
- **4) Удалить AmneziaWG**
- Создаваемые Mihomo-конфиги требуют Mihomo `v1.19.30+`

### Каскады — подменю

- **1) Добавить каскад** — два типа:
  - **iptables DNAT** — прозрачный proxy через netfilter для уже зашифрованного трафика (Reality / HY2)
  - **Shared listener** — добавить cascade-пользователя на существующий VLESS/Hysteria2 listener с под-правилом в IN-USER
- **2) Удалить каскад**

### Subscription hosting — подменю

После установки меняется набор пунктов:

| Пункт | До установки | После |
|---|---|---|
| **1)** | Установить | Статус |
| **2)** | — | Удалить |

Скрипт настраивает nginx, получает TLS-сертификаты через acme.sh и регистрирует директорию для per-client YAML + per-token nginx snippets. Два режима:

- **Порт 443 (nginx-integrated)** — разделяет порт с VLESS Reality через SNI routing (stream upstream). Нужен отдельный поддомен для подписок.
- **Кастомный порт (standalone)** — свой HTTPS-сервер, не зависит от VLESS.

Лимитирование: 10 req/min на IP, burst 5. Таймер `essence-sub-cleanup.timer` раз в 5 минут чистит просроченные подписки.

## Требования

- Debian / Ubuntu (с `apt`)
- Bash 3.2+
- Root-доступ
- Домен с A-записью, указывающей на IP сервера (для VLESS Reality в Self-Steal и для Subscription hosting)

При интерактивном запуске без root показывается exit-only экран с причиной и
командой повторного запуска. В remote-control ошибки подготовки зависимостей,
источника конфигурации и проверки пароля проходят через экран восстановления:
retry повторяет только неудачный этап, exit завершает процесс. EOF трактуется
как отмена, а не как подтверждение.

## Установка

```bash
curl -fsSL https://raw.githubusercontent.com/Morvex885/essence-setup/main/setup-essence/install-essence.sh | sudo bash
```

После установки:
```bash
sudo essence-setup
```

## Обновление

При запуске скрипт автоматически проверяет наличие новой версии. Для обновления выберите пункт **10) Обновить скрипты** в меню.

## Файлы после установки

| Путь | Описание |
|---|---|
| `/etc/mihomo/config.yaml` | Конфиг mihomo (сервер) |
| `/etc/mihomo/client-config.txt` | Готовый клиентский конфиг |
| `/etc/mihomo/reality.conf` | Параметры Reality (режим, ключи, SNI, домен) |
| `/etc/mihomo/certs/hy2/` | Самоподписанные сертификаты Hysteria2 |
| `/etc/mihomo/wgcf-profile.conf` | WireGuard-профиль WARP (если установлен) |
| `/etc/mihomo/subscription.conf` | Параметры Subscription hosting (URL, порт, режим) |
| `/etc/mihomo/amnezia/<peer>/` | Конфиги AmneziaWG peers + QR |
| `/etc/amnezia/amneziawg/awg0.conf` | Серверный AWG-интерфейс |
| `/etc/nginx/ssl/<domain>/` | TLS-сертификаты (Let's Encrypt) |
| `/etc/nginx/snippets/essence-sub/` | Per-token nginx-снипеты подписок |
| `/var/lib/essence-sub/` | Опубликованные `<token>.yaml` |
| `/var/www/<domain>/` | Decoy-сайт (при Self-Steal / SNI+cert) |

## Полезные команды

```bash
systemctl status mihomo              # Статус mihomo
journalctl -u mihomo -f              # Логи mihomo
nano /etc/mihomo/config.yaml         # Редактировать серверный конфиг
cat /etc/mihomo/client-config.txt    # Показать клиентский конфиг
awg show                             # Статус AmneziaWG
nginx -t && systemctl reload nginx   # Перезагрузить nginx после правок
```
